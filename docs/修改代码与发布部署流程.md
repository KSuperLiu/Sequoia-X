# Sequoia-X 代码修改与发布部署流程

本文档适用于当前 Sequoia-X 生产环境：

- 服务器：`root@172.93.187.65`
- SSH 私钥（本机）：`C:\Users\admin\.ssh\greenvps_key_fixed`
- 服务器项目目录：`/opt/sequoia-x`
- 当前部署分支：`codex/sequoia-trading-tracker`
- Docker Compose 服务：`api`、`worker`、`web`
- 持久化目录：`data/`、`logs/`、`backups/`


## 一、发布原则

1. 所有代码先在本机修改并完成测试，再提交到 GitHub。
2. 服务器只负责拉取已提交的代码和构建容器，不直接修改源码。
3. `.env`、数据库、日志和备份不得提交到 Git。
4. 发布前确认日常任务没有处于 `PENDING` 或 `RUNNING` 状态。
5. 发布前使用 SQLite 一致性备份接口备份两个数据库。
6. 生产服务器禁止执行 `git clean`、`git reset --hard` 或删除整个 `data/`。
7. 发布后必须检查容器、健康检查、任务状态和最近日志。

## 二、本机修改代码

### 1. 进入项目并同步部署分支

在 PowerShell 中执行：

```powershell
cd I:\TRAEWorkSpace\Sequoia-X
git switch codex/sequoia-trading-tracker
git pull --ff-only origin codex/sequoia-trading-tracker
git status --short --branch
```

如果 `git status` 显示已有未提交修改，先确认这些修改的来源，不要直接覆盖。

### 2. 为本次修改创建功能分支

分支名称建议使用 `codex/` 前缀：

```powershell
git switch -c codex/简短功能名称
```

例如：

```powershell
git switch -c codex/optimize-rps-memory
```

### 3. 修改并检查差异

完成代码修改后执行：

```powershell
git status --short
git diff --check
git diff
```

重点确认：

- 没有提交 `.env`、SSH 私钥、Webhook、密码或数据库文件；
- 没有误改 `data/`、`backups/` 和 `logs/`；
- 配置项变更同步更新了 `.env.example`，但示例中不能放真实密钥；
- 数据库结构变更兼容已有 `sequoia_app.db`。

## 四、提交并推送到 GitHub

### 1. 提交修改

```powershell
git status --short
git add <本次修改的文件>
git diff --cached
git commit -m "fix: 简要说明本次修改"
```

不要习惯性使用 `git add .`。明确列出文件，可以降低误提交配置和数据的风险。

### 2. 推送功能分支

```powershell
git push -u origin codex/简短功能名称
```

### 3. 合并到部署分支

在 GitHub 创建 Pull Request：

- 来源分支：`codex/简短功能名称`
- 目标分支：`codex/sequoia-trading-tracker`

确认测试通过并完成代码审查后再合并。服务器始终从
`codex/sequoia-trading-tracker` 拉取生产代码。

如果此次修改直接提交在部署分支上，则确认提交已推送：

```powershell
git push origin codex/sequoia-trading-tracker
```

## 六、发布前检查与备份

### 1. 检查服务和任务状态

```bash
docker compose ps
docker compose exec -T api python -c "from sequoia_x.app.db import AppDatabase; from sequoia_x.app.daily_job import get_daily_job; from sequoia_x.core.config import get_settings; s=get_settings(); print(get_daily_job(AppDatabase(s.app_db_path)))"
```

只有任务状态不是 `PENDING`、`RUNNING` 时才继续发布。任务正在运行时不要重启 `worker`。

### 2. 检查服务器工作区

```bash
git status --short --branch
git branch --show-current
git log -3 --oneline --decorate
```

当前服务器可能显示未跟踪的 `data/`，通常是 SQLite 的 `-wal`、`-shm` 文件。不要执行
`git clean`，也不要删除这些文件。

如果出现服务器源码的未知修改，停止发布并先查清来源。

### 3. 记录发布前版本

在当前 SSH 会话中执行：

```bash
PREVIOUS_COMMIT=$(git rev-parse HEAD)
echo "发布前版本：$PREVIOUS_COMMIT"
```

保留该值，用于紧急代码回滚。

### 4. 一致性备份数据库

```bash
docker compose exec -T api python -c "from sequoia_x.app.backup import backup_sqlite; print(backup_sqlite('data/sequoia_app.db','backups/manual','sequoia_app_predeploy',30)); print(backup_sqlite('data/sequoia_v2.db','backups/manual','sequoia_v2_predeploy',4))"
```

确认备份文件已经生成：

```bash
find backups/manual -maxdepth 1 -type f -name '*_predeploy_*.db' -printf '%TY-%Tm-%Td %TH:%TM %10s %p\n' | sort | tail
```

不要使用普通 `cp` 直接复制正在启用 WAL 的 SQLite 数据库作为唯一备份。

## 七、拉取并部署新版本

### 1. 拉取部署分支

```bash
git fetch origin
git switch codex/sequoia-trading-tracker
git pull --ff-only origin codex/sequoia-trading-tracker
git log -3 --oneline --decorate
```

`--ff-only` 可以防止服务器意外产生合并提交。如果拉取失败，不要强制覆盖，先检查
`git status` 和分支差异。

### 2. 构建并更新服务

```bash
docker compose build api worker web
docker compose up -d --remove-orphans
```

发布过程中 API 和网页可能有短暂中断。`data/`、`logs/`、`backups/` 是宿主机挂载目录，
正常重建容器不会删除这些数据。

如果新增了持久化目录，重新确认容器用户权限：

```bash
chown -R 10001:10001 data logs backups
```

### 3. 清理旧镜像（可选）

先确认新版本稳定，再执行：

```bash
docker image prune -f
```

不要使用带卷删除参数的命令，例如 `docker compose down -v`。

## 八、发布后验证

### 1. 检查容器

```bash
docker compose ps
```

预期结果：

- `api` 为 `Up` 且 `healthy`；
- `worker` 为 `Up`；
- `web` 为 `Up`。

### 2. 健康检查

```bash
curl -fsS http://127.0.0.1/health
```

命令应正常返回，且退出码为 0。

### 3. 检查最近日志

```bash
docker compose logs --since 10m --timestamps api worker web
```

重点检查：

- Python traceback；
- `ERROR`、`FAILED`、退出码 `-9`；
- API 健康检查失败；
- SQLite 锁冲突；
- Worker 重复领取或中断任务；
- Caddy 反向代理错误。

### 4. 浏览器验收

访问：

```text
http://172.93.187.65/
```

至少验证：

1. 管理员可以登录；
2. 核心看板可以加载；
3. 候选列表和股票详情可以打开；
4. 系统设置能读取任务状态；
5. 本次修改对应功能正常；
6. 页面没有持续的 401、500 或网络错误。

### 5. 查看生产版本

```bash
git rev-parse --short HEAD
git status --short --branch
```

生产提交应与 GitHub 部署分支最新提交一致。

## 九、代码回滚

仅在新版本出现严重问题时回滚。先保存故障日志：

```bash
cd /opt/sequoia-x
mkdir -p logs/deploy
docker compose logs --timestamps api worker web > "logs/deploy/failed_release_$(date +%Y%m%d_%H%M%S).log"
```

确认工作区没有未知的源码修改后，临时切换到发布前提交：

```bash
git status --short --branch
git switch --detach "$PREVIOUS_COMMIT"
docker compose build api worker web
docker compose up -d --remove-orphans
docker compose ps
curl -fsS http://127.0.0.1/health
```

这种方式只回滚代码，不回滚数据库。恢复正常后，应在本机对故障提交执行 `git revert`，
将回滚提交合并进部署分支，然后让服务器重新跟随部署分支：

```bash
git switch codex/sequoia-trading-tracker
git pull --ff-only origin codex/sequoia-trading-tracker
docker compose up -d --build --remove-orphans
```

如果新代码已经对数据库做了不兼容修改，不能只回滚代码。此时需要先停止 `api` 和
`worker`，核对准确的发布前备份，再执行数据库恢复。数据库恢复会覆盖发布后的业务数据，
必须单独确认后操作。

## 十、只修改单个部分时的快速部署

确认改动没有跨服务依赖时，可以只重建相关服务：

```bash
# 仅前端
docker compose up -d --build web

# 后端 API 和公共 Python 代码
docker compose up -d --build api worker

# 仅 Worker/任务逻辑，但公共镜像代码可能同时影响 API
docker compose up -d --build api worker
```

只要修改了 `pyproject.toml`、`uv.lock`、`Dockerfile`、公共 Python 模块或数据库结构，建议完整构建
`api worker web` 并完成全部验证。

## 十一、常用排障命令

```bash
cd /opt/sequoia-x

# 服务状态
docker compose ps

# Worker 最近 200 行日志
docker compose logs --tail 200 --timestamps worker

# API 最近 200 行日志
docker compose logs --tail 200 --timestamps api

# 实时跟踪日志，按 Ctrl+C 退出
docker compose logs -f --tail 100 worker

# 资源使用
docker stats --no-stream
free -h
df -h / /opt/sequoia-x

# 内存不足记录
journalctl -k --since today --no-pager | grep -Ei 'oom|out of memory|killed process'

# 当前代码版本
git status --short --branch
git log -5 --oneline --decorate
```

当前服务器只有约 1 GB 内存。运行全量 Pandas 策略时应特别关注 OOM；发现退出码 `-9` 时，
优先检查内核 OOM 日志，不要反复重试任务。
